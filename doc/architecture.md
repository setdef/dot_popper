# Dot Popper's architecture

How Dot Popper's code is divided, what each part may depend on, and how a press, a frame and a save move through it. It is for anyone, person or coding agent, about to change the code. The words are `GLOSSARY.md`'s. Why each large choice was made is in the [decision log](adr/README.md); how each area works in detail is in the [design documents](#design-documents).

## The parts

Dot Popper is Ruby on [Lota](https://github.com/setdef/Lota), which runs LÖVE's engine with Ruby in place of Lua. The code is in four layers, the composition root that puts them together, an edge, and code outside the game.

| Part | Where | Holds | May use |
| --- | --- | --- | --- |

### The rules between them

- **Only the shell calls Lota.** The core, the use cases, the presentation and the composition root name Lota only in comments, so all of their tests run without a window (`AGENTS.md` makes this a rule), and the engine's own names for things (a system's name, among others) stop at the shell. Code that needs the engine to decide something, such as measuring text, takes it as an argument: the presentation measures with whatever it is given (`Shell::FontMeasure` in the game, `RoughMeasure` in tests).
- **Dependencies point inward.** The core names nothing in the use cases, the presentation or the shell; the use cases name nothing in the presentation or the shell; the presentation names nothing in the shell; the composition root names nothing in the shell, which hands it what it needs. `lib/dot_popper/privacy/` is the exception, by design: it is not loaded by the game, and reads the presentation's words to write the privacy document.
- **Each area names only what the context map lets it.** Gameplay and Metagame names nothing of Monetization or Release Engineering, so the rules of play never know that Pro exists; Monetization may hear Gameplay's events; Release Engineering, which has no interface at run time, names neither and is named by neither; and none names the use cases, the presentation, the shell, the composition root or the privacy declarations. Each may name the code they share (`Network`, `Platform`, `Automation`, and `MemoryFile`, a save file kept in memory). The shared code names nothing of the three, so it never carries one area to another. `test/areas_test.rb` resolves every constant that an area's Ruby (its folder and its loader) or the shared code names, as Ruby would, and fails on any other (it lists none today: a breach would be listed with the step that removes it). Monetization does not ask the build's channel: the composition root reads it and hands Monetization what it means. Each area loads by itself from its own loader (`dot_popper/gameplay.rb` in Gameplay's gem, `lib/dot_popper/monetization.rb`, `release_engineering.rb`), with nothing of the game but the shared code it names (`test/area_loaders_test.rb`). Steep checks each area in a target that loads only the signatures it may name ([development](design/development.md#steep-in-strict-mode)). Neither sees a constant reached by a name spelled at run time.
- **The core is mostly values.** Dots, the `Stack`, the field, the clock (`Clock`), spawns, `GameStats`, Stats, the rules' numbers and every event are immutable `Data` values, frozen deeply enough to be shared between Ractors (`test/ractor_test.rb`), and changes return new values. A few objects change in place, each by swapping in new values: `GameFlow`, which holds the current state and is the one object players' presses reach; the `Game` it holds while a game is paused, in play or just over; the objects that keep what is saved (`ScoreRecord`, `SavedStats`, `StatsBackup`, `Achievements`, `FreeGames`, `Entitlement`); the listeners that count a game as it plays (`AchievementRecorder`, `GameStats::Recorder`, `GamesLog`); and friend groups' client (`Groups::Session` with its `Unsent` and `KnownGroups`), which changes its lists in place.
- **The core and the use cases are typed.** `rake steep` checks two projects, each against `sig/` in strict mode ([development](design/development.md#steep-in-strict-mode)). The first checks the use cases with `lib/dot_popper.rb` and `lib/dot_popper/*.rb`, against all of `sig/` and the signatures of the game's own gems. The second keeps the areas apart: each area is a target of its own, which loads only its own signatures and those of the code the areas share (Gameplay's gem, `gems/dot_popper-gameplay/lib/**/*.rb`; all of Monetization, `lib/dot_popper/monetization/**/*.rb`, with the website part's license keys and store and each store's part's receipt check (`apple/`, `play/` and `microsoft/receipt.rb`); `lib/dot_popper/release_engineering/*.rb`), and the shared code (`network.rb`, `platform.rb`, `automation.rb`, `memory_file.rb`, in `gems/dot_popper-shared`) is a fourth target, which loads only its own. Each of the game's own gems also checks itself with its own signatures and those of the gems it names, no others. The presentation, the composition root, the shell, `network/`, the rest of the website part and the test build's part are not typed.
- **Every outside party is behind a port.** The network is reached only through `Network::Link`, by a request made only from its declaration ([privacy](design/privacy.md#requests)); a store only through the store port, `Store` ([store and Pro](design/store-and-pro.md#the-store-port)); a file only through `Shell::SaveFile`; the system's share sheet and stores only by a URL the host catches or a helper process ([ADR-0008](adr/0008-native-features-live-outside-the-ruby-process.md)). Tests source-scan for the first and third ([privacy](design/privacy.md)).
- **The build decides what it trusts.** `Build::CHANNEL` is nil in a test build (every playtest kit and CI run) and names a store in a store build. It alone chooses the store's adapter, the keys and receipts trusted, and which `DOT_POPPER_*` settings are obeyed ([ADR-0010](adr/0010-pro-comes-only-from-proof.md)). The composition root chooses the keys and receipts trusted by the channel (`Root.pins`, `Root.license_signing_keys`, `Root.receipt_trust`), Monetization decides the rest from it in the core (`Store.for`, `LicenseKeys::License.kept_in`, `FreeGames.metered?`), and the root asks them and connects what they answer (`test/composition/root_test.rb`). `script/check_build.rb` asks a built app's own `Root.pins`, `Root.license_signing_keys` and `Root.receipt_trust`, and its `Build.settings`; it does not check which store the app sells through, where it keeps a license key, or who it meters. The game reads the environment only through `Build.settings`, which `Composition::DeveloperSettings` wraps.
- **Automated runs reach no outside host.** A test, a GUI scenario, the bot, or any run told to quit or take screenshots by itself sets `Automation.on?`, and `Automation.guard!` then refuses every connection to a host that isn't this machine.

## The game as a state machine

`GameFlow` (`gems/dot_popper-gameplay/lib/dot_popper/gameplay/game_flow.rb`) is the game as a whole. Its state is one of four values, `Home`, `Paused`, `Playing` and `GameOver`, each answering `press(x, y)` and `update(seconds)` with the state that follows. A press on Home reaches no rule: a game begins only when it is started, through the game flow's `GameFlow::Starter` (`#game`, or `#paused` for the tutorial), which `GameFlow#starter` hands out once and the composition root gives `UseCases::StartGame`, so nothing else is handed the means to start one: the game flow has no method of its own that starts a game (`gems/dot_popper-gameplay/test/dot_popper/gameplay/game_flow_test.rb`), and `test/use_cases/start_game_test.rb` fails if any other file in the game's code takes the Starter or reads it by reflection (`@starter`). Ruby cannot forbid reflection, so a name spelled at run time would pass that scan. The game is a `Game` (`gems/dot_popper-gameplay/lib/dot_popper/gameplay/game.rb`): the field, the `Stack` of dots, the `Clock`, the score, and the `Spawner`. Only `GameFlow` holds it; its states, and anyone who asks (`GameFlow#game`), get its read-only `Game::View`, made once with the game, which answers what the game is and nothing that changes it, so the screens, the renderer, the bot and the tutorial read the game each frame without being able to change it (`gems/dot_popper-gameplay/test/dot_popper/gameplay/game_flow_test.rb` fails if anything the game flow answers can). Only a press at a place reaches the game, so no key or gamepad button can touch the score or the clock, and nothing outside `Playing` changes either, except a `Paused` game while the tutorial plays over it. A game is finished, an event announced and Home shown only by the game flow's own states, through the `GameFlow::Transitions` it hands them as it passes on a press or an update, so nothing that holds the game flow can have a game that was never played counted in Stats or sent to friend groups (`gems/dot_popper-gameplay/test/dot_popper/gameplay/game_flow_test.rb`); `UseCases::FinishGame` likewise finishes a game only as it hears the game's `GameEnded`.

Each change is announced as an event (`gems/dot_popper-gameplay/lib/dot_popper/gameplay/events.rb`): `Popped`, `MistakeMade`, `Missed`, `GameStarted`, `GameEnded`, `HomeShown`. An event is a value made after the change, carrying what a listener needs of the game as it then stood, under `Game`'s own names (the field, the dots, the score, the clock, the time played, the row), and never the `Game` itself: a listener reads the game from its events alone, so one that keeps an event never sees later play through it (`test/ractor_test.rb` fails if any event can't be shared). `GameFlow` tells every listener in order. Nothing in the core, the use cases, the presentation or the composition root subscribes itself: the composition root subscribes `UseCases::FinishGame` (which passes each event to its `GameStats::Recorder` and `AchievementRecorder`), then the `Show`, `Refresh` and `GamesLog` (`games.csv`), and the shell's `App#load` then subscribes the `Pile`, `Tilting` and `Dragging`. In the shell, `Shell::DevelopmentHooks` subscribes itself as it is made, when a development setting asks it to meter frames. A listener that holds the `GameFlow` can read the game as it stands (`GameFlow#game`, a `Game::View`) but not change it.

Screens other than Home, a game and Game Over (Settings, Stats, Achievements, Themes, Friend groups, the Pro offer, Credits, Privacy, the share preview, the tutorial) are the presentation's alone: each is a screen object (`Presentation::Screens`) that the `Show` opens on its stack over Home or Game Over, and the one on top answers every input ([screens](design/screens.md#screens-as-objects)); a press there never reaches `GameFlow`. The tutorial is the exception: it is a layer over a real game, which `GameFlow` holds `Paused` before its clock first runs (`GameFlow::Starter#paused`). The tutorial moves that game's dots at its own pace and passes it only the presses it chooses (`GameFlow#press_paused`, whose events come back to it and are announced to no one); when it ends or is skipped, the same game plays on (`GameFlow#unpause`, which announces `GameStarted`; [tutorial](design/tutorial.md)). Every way into a game, Play or the tutorial's opening, goes through `UseCases::StartGame`, which spends a free game ([store and Pro](design/store-and-pro.md#free-games)).

## Use cases

The game's domain is in three areas, the maintainer's division ([ADR-0019](adr/0019-clean-architecture-and-domain-driven-design-in-three-areas.md)): Gameplay and Metagame (playing, Stats, records, achievements, today's goal, friend groups and the title, themes), Monetization (Free and Pro, free games, locked features, the stores, receipts, license keys, proof that setdef is there), and Release Engineering. Each is a module, with a folder of its own or a gem (`gems/dot_popper-gameplay` is `DotPopper::Gameplay`; `lib/dot_popper/monetization/`, `release_engineering/`), and what each may name is held by a test and by Steep ([the rules between them](#the-rules-between-them)). The rules of play never know that Pro exists, so a rule that needs both of the first two lives in a use case (`lib/dot_popper/use_cases/`, `DotPopper::UseCases`), outside both and outside the screens. Each is an object made with its collaborators by the composition root (`Composition.use_cases`, which also subscribes each to what it hears; `UseTheme`, which hears nothing, the root makes first, for the theme the game starts in), handed to the `Show`, and called from a screen (all but `FinishGame`, which hears the rules' events instead), whose screen carries out what it answers; each is tested in `test/use_cases/` with save files in memory and local fakes. The `Show` and its screens are never given what decides Pro (`Entitlement`, `FreeGames`, the stores, `LicenseKeys::License`), only the use cases that ask it, and only the offer of Pro (`Screens::Offer`) is given `BuyPro`. `test/use_cases/pro_knowledge_test.rb` walks the game as the root builds it and fails if anything in the presentation holds one of those, outright or in a block it keeps; and, as a second line, fails if anything in `lib/` outside Monetization's own code, the use cases and the composition root names them or asks `pro?`, or if the presentation or the shell names a use case's `locked?` or `owned?`. Neither sees a constant or a global reached by a name spelled at run time. As a third, by behavior, it builds the game for a Free player and for a Pro player and fails if the `Show`, a screen or the friend groups' panel answers any public question (a method ending in `?` that needs no argument) differently for the two, on Home, at Game Over and on Home again. The use cases' answers still tell Free from Pro, as the words and screens that carry them out must, so a decision made on one inside a command, or under a name that is not a question, passes all three, and only review stops it.

| Use case | Does | Takes | Answers |
| --- | --- | --- | --- |
| `StartGame` | Starts a game from Home and spends one free game on it: in play at once for Play, or paused with the tutorial's first dot (`TutorialScene.opening`) for the tutorial, which is spent as it opens. With none left nothing starts, and it answers the offer of Pro, which Home's Play and Game Over's Play again open: games run out only where they are counted, which is only for a Free player where Pro is offered (`FreeGames.metered?`). | `GameFlow`, `FreeGames` | `:started`; `:offer` with no game left, wherever it is asked; or `:not_home` away from Home with a game left, where Game Over's Play again goes Home and asks again; `#none_left?` says beforehand whether Play would lead to the offer, for Play's word; `#left` and `#daily` how many games are left and come each day, nil where none are counted |
| `FinishGame` | Hears the rules' events, counting each game's numbers (`GameStats::Recorder`) and the achievements its play earned (`AchievementRecorder`), and finishes a game as `GameEnded` is heard: adds it to Stats with the records it set and today's goal, keeps the achievements it earned for anyone, tells friend groups of a game that counts (never one the tutorial opened, which `GameEnded#tutorial` says), and, for Pro alone, reports its new achievements and lets Game Over show them. | `SavedStats`, `Achievements`, `Entitlement`, the friend-group session | what Game Over shows, told to its listeners (`#subscribe`) as each game is finished (`FinishGame::Finished`: the game's `GameEnded`, its numbers, and the record set, the goal met and the achievements to name); and the numbers of the game in play (`#stats`) |
| `BuyPro` | The offer's actions: asks the store as the offer opens; Buy, or Try again before a price has come; Restore Purchases. Buy does nothing once the player has Pro. Hears the store only while no game is in play, and when Pro arrives reports the achievements already earned to friend groups. The offer's one way to the store and to Pro. | the store port (`DotPopper::Monetization::_Store`), `Entitlement`, `GameFlow`, `Achievements`, the friend-group session | whether Pro is offered, which only the offer of Pro asks and keeps to itself, whether Buy was taken, and what the offer shows of the store: whether it sells, its price and its status. On a website copy the offer's second action, the website part's, enters a license key through `EnterLicenseKey` (`lib/dot_popper/website/offer.rb`), the one way to the website store's keys |
| `UseTheme` | Uses a theme the player chose, if they have Pro and it is open; says which theme is current (a Pro player's choice, the ordinary one for Free), taken up only between games. | `SavedThemes`, `Entitlement` | `:used`, `:same`, or `:offer` for a Free player; `#choice` what choosing a theme would lead to, for the new theme card's word: `:use`, `:same`, or `:offer` for a Free player |
| `JoinOrCreateFriendGroup` | Joins or creates a friend group for a Pro player; leaving and deleting never need Pro, so they are not here. | the friend-group session, `Entitlement` | `#start` (as Join or Create is pressed, before the notice or the code pad) `:go`, `#join` and `#create` `:sent`, each `:offer` for a Free player, which the friend groups' panel acts on |
| `ViewAchievements` | Says what the Achievements screen and its dialog may show: for Pro which are earned, the day, how many, and how far along the four measured ones are; for Free none of it. | `Achievements`, `Entitlement`, `SavedStats`, `ScoreRecord` | each of those, or nil while locked (`#earned?` false); `#status`, for the dialog, `:earned`, `:not_earned`, or `:offer` for a Free player |

The `Show` lays out Game Over when `FinishGame` tells it a game is finished, not when it hears `GameEnded` itself, so what Game Over shows is the game's own whatever order the listeners hear the rules in (`test/presentation/show_test.rb` has a `Show` hear them first). The score record is judged by `GameFlow` as the game ends and carried by `GameEnded`, as before: a record is the same area as the game, so no rule of Pro is in it, and moving it would change what `GameEnded` carries for every listener with no rule gained.

Changes that another area cares about are announced by the object that knows, rather than found by the `Show` comparing before and after: `Entitlement` announces `Entitlement::ProGranted` when Pro arrives ([store and Pro](design/store-and-pro.md#the-store-port)), and `Continuity::Gone` announces `SetdefGone` or `SetdefHere` with each check it takes up, which `SavedThemes` and `ServerChoice` hear through a port Gameplay owns: the composition root's `Composition::SetdefAdapter` tells them each as Gameplay's own value, `Gameplay::SetdefGone` or `Gameplay::SetdefHere`, so neither area names the other ([when setdef is gone](design/store-and-pro.md#when-setdef-is-gone)).

These rules once lived in the `Show`, beside what each screen draws, where the one way into a game was a private method that a press on `GameFlow`'s Home could bypass, and the rules could be tested only through the screens. Each rule could instead have gone in the area it mostly concerns, telling that area about the other, but then `GameFlow` would know that games are counted for a purchase, and the achievements would know Pro. One Monetization question, "what does Pro unlock here?", in place of the three small use cases for themes, friend groups and achievements, would leave each screen to decide what a locked answer means. Coding agents chose use cases under the maintainer's decision to follow Clean Architecture and Domain-Driven Design. The cost: one more layer to follow from a press to a rule, an RBS signature for each use case with interfaces for the collaborators the core does not type, three use cases that hold little more than one question of Pro each, and `BuyPro` passing on what the offer shows of the store, since the offer reaches the store only through it.

`StartGame` spends in the same call that starts the game, before it starts, as the `Show` did. Spending as an echo of the game's own `GameStarted` was weighed and set aside: a game the tutorial plays over announces `GameStarted` only as play begins, after the tutorial, but is spent as it opens ([tutorial](design/tutorial.md#what-spends-a-free-game)), so the echo would move the spend, or need an event the rules make only for Monetization.

## A frame

Lota calls `main.rb`'s callbacks; each goes straight to `Shell::App` (`lib/dot_popper/shell/app.rb`).

1. **Inputs.** Each input callback (a mouse, a finger, a gamepad's button or trigger, a key, the wheel, focus) goes to `Shell::LotaInput`, which turns it into the game's own event (`Presentation::MousePress`, `ButtonPress`, `KeyPress` and the rest) by the game's names, and `App` hands that to its one entry point, `Presentation::InputHandler#call`. The shell names each input and decides almost nothing about what it means ([input.md](design/input.md), "What the shell still decides"). The handler does: `Chatter` drops a failing mouse's double click; `InputRouter#tap` leaves out what is no press of the player's own (SDL's made-up mouse for a finger, a mouse's side buttons, a trackpad's touches) and turns the rest into a `Tap`; a `Tap` goes to `Show#tap`, which hands it to the screen on top (`Show#screen`): a button's, empty space's, the tutorial's, or a game's, which passes it to `GameFlow#press` on the frame it happened; on Game Over a press away from the buttons goes to the pile instead (`Shell::Dragging`). A gamepad's A presses at its cursor through the same path; its other buttons and the wheel go to what the screen on top answers (`Show#pad`, `#start`, `#back`, `#wheel_scroll`), and a key to the first `KeyBinding` that takes it, of the screen on top's own (`Screens::Screen#key_bindings`) and then the handler's (`InputHandler::KEY_BINDINGS`), in the order `doc/design/input.md` gives. What only the engine can do (the splash, quitting, fullscreen) the handler asks of the `App`.
2. **Time.** `Lota.update` calls `App#tick`, which measures the time between the last two frames starting to draw (`FrameClock`), not Lota's own `dt`, and clamps it to `Rules::LONGEST_FRAME` (0.1 seconds).
3. **Update.** `App#update` hands the sticks to the `InputHandler`, which moves the gamepad cursor (or scrolls a list), then moves the bot if it plays, `GameFlow`, the `Show` (its effects, animations, HUD, the screens' state, the store's answers through `UseCases::BuyPro`, and the friend-group session), the theme releases' replies (`ThemeReleases#update`) and the setdef watch, then the shell's tilt, drag, pile physics and particles, and, where a development setting asks for them, the screenshots, the quit and the frame meter (`Shell::DevelopmentHooks`).
4. **Draw.** `Lota.draw` calls `Renderer#draw`, which draws the `Show`'s state through the `DrawingContext` and the painters straight to the window at its own pixels: the night, the dots and their glow (or the pile after time's up), effects, Game Over's words and the HUD, then the screens open over the game's state from the last that covers the rest up to the top one (`Show#stack`), and the gamepad cursor.

The GUI scenarios replace step 2 with a fixed step and push presses onto Lota's event queue, so everything else runs as a player's game does ([development](design/development.md#the-gui-scenarios)).

## Composition

`Composition::Root` (`lib/dot_popper/composition/root.rb`) is the composition root. It decides, in plain Ruby with no Lota, what the game is built from on its `Platform` and in its kind of build (`Build::CHANNEL`), and builds it: it has the window opened (a phone's screen filled, a computer's window sized), makes every save file, the `GameFlow` with its `ScoreRecord`, `SavedStats`, `Achievements` and `StatsBackup`, the license key, in a build with the website's part (`lib/dot_popper/website/`, PACKAGING.md), in the save file where Monetization keeps one (`LicenseKeys::License.kept_in`), and the setdef watch, both given the pins the build trusts (`Root.pins`), the `Entitlement` with that license and the receipts the build trusts (`Root.receipt_trust`), the store for this build (`Store.for`), `FreeGames`, metered as `FreeGames.metered?` says, the friend-group `Session` and the server it uses (`ServerChoice`), the player's `SavedThemes`, `UseCases::UseTheme` (whose current theme's art the `DrawingContext` and the `SoundPlayer` take at launch), the other use cases (`Composition.use_cases`), `ThemeReleases`, haptics and sharing for the platform, the splash, the `Show`, which takes the use cases and the presentation's own collaborators as arguments, the games log, the gamepad cursor and the bot. It subscribes every listener it makes itself, and nothing it makes subscribes itself: `FinishGame` to `GameFlow` and `BuyPro` to `Entitlement` (in `Composition.use_cases`); then the `Show` to `GameFlow` and to `FinishGame`, which tells it each game it finishes for Game Over, and the offer of Pro to `Entitlement`, so a purchase ticks on it after friend groups are told; the `ServerChoice` and `SavedThemes` to `Continuity::Gone`, through `Composition::SetdefAdapter`; and `Refresh` and the playtest log to `GameFlow`. `test/composition/root_test.rb` checks the order, that making a `Show` subscribes nothing, and that the `Show` it builds lays out the Game Over of a game played there. Nothing it makes reaches past the process until `Root#start` (the first request for theme releases, the store's first question, the setdef watch).

What only the engine can make or do, the root asks of an engine it is given, whose methods it lists: a save file by name, what a graphics unit is called, the window's size and layout, opening the window, the `DrawingContext`, the `SoundPlayer`, text measure, the clipboard, the URL opener, the vibration motor, the notices, the store helper and the store's answer file. In the game that is `Shell::Engine`. The developer settings it obeys are `Composition::DeveloperSettings`, the environment as the build allows (`Build.settings`), which `Shell::App` makes once.

`Shell::App#load` makes the `Engine` from the `Platform` the shell makes of `Lota::System.os` (`Shell::Platforms`), hands it to the root, and then makes only what carries the game out with Lota: the Game Over `Pile`, `Gamepads`, `Tilting`, `Dragging`, the particles and the `Renderer`, in the styles the root chooses. `test/composition/root_test.rb` builds the root for every system and every channel, with save files in memory and a fake engine (`test/composition/fake_engine.rb`), and checks each of those choices; presentation tests build a `Show` as the root does, through `PresentationTest.show`, with save files in memory in place of files on disk.

`conf.rb` runs before all of this, and before the window opens: it names the save folder (`t.identity`), sets the window, and chooses the renderers, with the rescue that starts the game again without Vulkan when Vulkan can't start it ([platforms](design/platforms.md#the-vulkan-rescue)).

## Saving

Everything the game keeps is a text file in Lota's save folder, read and written whole through `Shell::SaveFile`, which refuses any name not declared in `Privacy::SAVE_FILES`. Lota's save folder can't rename or append, so a file is rewritten whole, and a backup is a copy written before the original changes. The core's objects that keep what is saved (`ScoreRecord`, `SavedStats`, `FreeGames`, `License` and the rest) each take a save file that answers `read` and `write(text)`, so they work on one in memory in tests. Gameplay keeps each save file's format apart from the rules of what it holds, in a value of its own that parses the text and writes it back (`ScoreRecordFile`, `StatsFile`, `AchievementsFile`, `ThemesFile`, `Groups::GroupFile`), so the rules never parse and the formats hold no rule. Saves read leniently: a line that can't be read keeps its starting value. `doc/privacy.json` lists every file, what it holds, and what leaves the device.

## Threads

The game runs on Lota's one thread. Friend groups' requests and the theme releases' each run on a `Network::Worker`'s thread, at low priority, started by its first request, so a player with no friend group has no thread for them; the setdef watch has a thread of its own. A frame reads finished replies and never waits. The simulator and one test use Ractors; the game does not.

## Platforms

One code base runs on macOS, Windows and Linux (built by `lota fuse`, [PACKAGING.md](../PACKAGING.md#lota-fuse)) and on iOS, iPadOS and Android (built by Lota's phone guide with Fledge). The shell makes one `Platform` value from Lota's name for the system (`Shell::Platforms`), and everywhere else the game asks it its own questions (is this a touch device, does it quit itself, does it buzz, which store is its own), so nothing beyond the shell names a system. The differences are in a few places: `DotSize.for`, `Entitlement.forced?`, `Shell::Haptics`, `SheetSharing.for` and `Store.for` by platform; `conf.rb`'s renderers; the phone hosts' native files; and the desktop's window controls (`Shell::DesktopWindow`). [Platforms](design/platforms.md) has the details.
